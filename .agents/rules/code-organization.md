# 代码组织与文件规模规则（Code Organization）

> 目标：让任何源文件都能被快速阅读与审查。可维护性远比追求极端行数数字更重要。

## 1. 阈值（团队约定）

| 类型 | 预警线（开始审视） | 上限（必须拆分） |
|------|------------------|-----------------|
| 业务源文件（.rs / .ts / .tsx / .go / .kt） | **400 行** | **500 行** |
| 测试文件 / 集成测试 | 800 行 | **1000 行** |
| 生成的代码（proto 生成、tauri gen） | 不适用 | 不入此规则（但不要手改） |

- 文件达到预警线时就应该开始思考如何拆分，而不是等到突破上限。
- 行数不是银弹：一个 400 行但职责单一的模块，优于为凑数字而机械切碎的 4 个 100 行碎片。

## 2. 以「单一职责」为纲

拆分的唯一正当理由是职责分离。判断信号：

- 一个文件里出现多个互不相关的 pub 功能域（如命令注册 + 视图转换 + 校验 + 业务逻辑）
- 文件注释里需要写"本文件负责 A、B、C"才能说清它干什么
- 改 A 功能时总要滚过 B、C 的代码
- 测试需要 mock 掉同文件里大量不相关内容

## 3. 模式先行（按代码性质选拆分模式，不随意切割）

### Rust

- **按职责子模块**：`foo.rs` → `foo/mod.rs` + `foo/{bar,baz}.rs`（或同级 `foo_bar.rs`），`mod` 声明按字母序
- **impl 分块**：巨型 struct 的多个 impl 块按能力域拆到不同文件（`impl Xxx` 可跨文件，同一 crate 内自由分布）
- **路由按资源域**：axum routes 一资源一文件（参照 pp-hub/src/routes/ 现有结构）
- **命令按域拆分**：Tauri/CLI 命令按功能域分文件（`commands/nodes.rs`、`commands/mitm.rs`…），壳文件只做注册
- **纯逻辑下沉**：校验/转换/格式化等无 IO 纯函数下沉到库 crate（可单测），UI/壳层只做绑定
- **测试同行**：内联 `#[cfg(test)]` 随模块走；测试文件超限时按被测域拆 `tests/` 子模块

### React / TypeScript

- **页面 = 组合，不是巨兽**：页面组件只组合区块与处理路由级状态；表格、弹窗、表单各自成为子组件（`pages/Nodes/index.tsx` + `pages/Nodes/InstallWizard.tsx` …）
- **Hooks 抽逻辑**：数据获取/轮询/表单状态抽 `useXxx` hook（放 `src/hooks/` 或页面同目录）
- **Services/API 层分离**：API 调用只在 `src/api/`，页面不直接写 axios 细节
- **弹窗独立**：一个 Modal 超过 ~80 行就独立成组件文件
- **i18n 先行**：文案 key 与组件同步增长，不把大段 JSX 留在页面里"以后再拆"

### Go / Kotlin（Android）

- 一文件一类型/一能力域；接口与实现分文件
- 平台胶水（gomobile 导出、Tauri 插件）与业务逻辑分文件

## 4. 及早重构

- PR/提交时若文件越过预警线，在提交信息或 PR 描述里说明"为什么现在不拆"或顺手拆
- 新功能优先建新模块，而不是往已超线的文件里塞

## 5. 工具检查（建议）

- 预警线检查可在 CI 加脚本（示例）：
  ```bash
  find crates apps -name '*.rs' -o -name '*.ts' -o -name '*.tsx' \
    | grep -vE 'target/|node_modules/|/gen/|dist/' \
    | xargs wc -l | awk '$1 > 500 && $2 != "total" {print}' 
  ```
  超限列表仅告警，不强制阻断（生成物与特殊文件允许例外并在 PR 中说明）

## 6. 验收标准

拆分重构必须满足：

1. 行为完全不变（纯重构，不改语义）
2. `cargo test --workspace` / `bun run verify` 全过
3. `pub` 可见性不扩大（能不 pub 就不 pub）
4. 原子化提交：一个文件的拆分为一个提交
